# Design: Remove LangGraph From Orchestration

Generated by /office-hours on 2026-04-30
Branch: develop
Repo: CompSynth
Status: DRAFT
Mode: Builder / Engineering

## Problem Statement

CompSynth currently uses LangGraph for the main content pipeline, but the graph only models a fixed async flow:

```text
fetch_sources
  -> deduplicate
  -> summarize -> enrich -> publish
  -> use_last_digest
  -> end
```

The project goal is twofold:

- Internal engineering speed: remove an unnecessary runtime dependency and reduce maintenance cost.
- Open-source architecture quality: make orchestration easier to read, test, and modify without requiring LangGraph knowledge.

## What Makes This Worth Doing

LangGraph is useful when the application needs graph execution, checkpointing, persistent state, retries across graph nodes, human-in-the-loop control, or complex branching. CompSynth currently uses it as a thin wrapper around ordinary Python control flow.

Removing it should make the main execution path more direct:

```text
main.run()
  -> run_pipeline(initial_state)
  -> fetch_sources()
  -> deduplicate()
  -> branch on new_items / last digest
  -> summarize()
  -> enrich()
  -> publish()
```

## Current Code Surface

Observed relevant files:

- `src/comp_synth/orchestration/graph.py` imports `StateGraph` and `END`, builds the graph, and exposes `route_after_deduplicate()` plus `build_pipeline()`.
- `src/comp_synth/main.py` imports `build_pipeline()` and calls `await pipeline.ainvoke(initial_state)`.
- `tests/test_pipeline_nodes.py` imports `route_after_deduplicate()` from `graph.py`.
- `pyproject.toml` declares `langgraph>=0.2`.
- `uv.lock` includes `langgraph`, `langgraph-checkpoint`, `langgraph-prebuilt`, and `langgraph-sdk`.
- `CLAUDE.md` and `docs/Architecture.md` describe orchestration as a LangGraph pipeline.

## Premises

1. The pipeline is intentionally linear with one simple route after deduplication.
2. The project does not currently need LangGraph checkpointing, persistent graph state, human-in-the-loop pauses, or graph-level concurrency.
3. A plain async function is easier for contributors to understand than a graph builder for this workflow.
4. Behavior must remain unchanged: missing subscriptions, empty subscriptions, no-new-content reuse, successful publish, and error propagation should work the same.
5. Dependency removal is not complete unless `pyproject.toml`, `uv.lock`, tests, and docs stop referencing LangGraph.

## Approaches Considered

### Approach A: Compatibility Wrapper

Summary: Keep `build_pipeline().ainvoke(initial_state)` as the public shape, but replace LangGraph with a tiny local class exposing `ainvoke()`.

Effort: S
Risk: Low

Pros:

- Minimizes changes to `main.py` and any external code that might call `build_pipeline()`.
- Lets implementation remove the dependency quickly while preserving the old invocation shape.

Cons:

- Keeps a fake graph abstraction after removing the actual graph framework.
- Future contributors still have to ask why a pipeline object exists for a fixed function call.

Reuses:

- Existing `route_after_deduplicate()` and node functions.

### Approach B: Plain Async Pipeline

Summary: Replace `graph.py` with a plain orchestration function, likely `run_pipeline(initial_state: PipelineState | None = None) -> PipelineState`, and update `main.py` to call it directly.

Effort: S
Risk: Low to Medium

Pros:

- Removes the graph concept entirely, which matches the current workflow.
- Makes the branch behavior visible in normal Python code.
- Tests can assert pipeline behavior without compiling or invoking graph objects.

Cons:

- Any external code importing `build_pipeline()` would need to migrate.
- The implementation must carefully preserve state merge semantics from LangGraph node returns.

Reuses:

- Existing node functions in `src/comp_synth/orchestration/nodes.py`.
- Existing `PipelineState` type, with docstring updated to remove LangGraph wording.
- Existing route test, moved to the new pipeline module.

### Approach C: Small Step Runner

Summary: Introduce a local step runner with named async steps and route functions, but no LangGraph dependency.

Effort: M
Risk: Medium

Pros:

- Keeps named steps and routing if the pipeline is expected to grow.
- Could make tracing or structured execution logs easier later.

Cons:

- Replaces one framework with a smaller local framework before the project clearly needs it.
- More code than the current workflow deserves.

Reuses:

- Existing node functions and route function.

## Recommended Approach

Choose Approach B: Plain Async Pipeline.

This is the cleanest match for the stated goals. It removes both the dependency and the mental model. The core implementation should be boring Python:

```python
async def run_pipeline(initial_state: PipelineState | None = None) -> PipelineState:
    state = default_pipeline_state()
    if initial_state:
        state.update(initial_state)

    state.update(await fetch_sources(state))
    state.update(await deduplicate(state))

    route = route_after_deduplicate(state)
    if route == "end":
        return state
    if route == "use_last_digest":
        state.update(use_last_digest(state))
        return state

    state.update(await summarize(state))
    state.update(await enrich(state))
    state.update(await publish(state))
    return state
```

## Implementation Plan

1. Rename or repurpose `src/comp_synth/orchestration/graph.py` to expose plain pipeline helpers.
   - Preferred name: `pipeline.py`.
   - Keep `route_after_deduplicate()` unless tests or call sites benefit from inlining it.

2. Update `src/comp_synth/main.py`.
   - Replace `build_pipeline()` and `pipeline.ainvoke(...)` with `run_pipeline(initial_state)`.

3. Preserve state behavior.
   - Node functions return partial dicts.
   - The pipeline must `state.update(...)` after each node, matching LangGraph's accumulated state behavior.
   - `use_last_digest()` is sync today, so call it directly unless converting all nodes to async buys consistency.

4. Remove LangGraph dependency.
   - Delete `langgraph>=0.2` from `pyproject.toml`.
   - Regenerate `uv.lock` with `uv lock` or equivalent project workflow.
   - Confirm no `langgraph`, `langgraph-checkpoint`, `langgraph-prebuilt`, or `langgraph-sdk` remains in the lockfile unless another dependency pulls them in.

5. Update tests.
   - Change imports from `comp_synth.orchestration.graph` to the new module.
   - Add a focused test for the no-new-items branch:
     - no new items + last digest exists -> `use_last_digest`.
     - no new items + no last digest -> returns without publish.
   - Add a small pipeline-order test using monkeypatched node functions if practical.

6. Update docs.
   - `CLAUDE.md`: replace "LangGraph pipeline" with "plain async pipeline".
   - `docs/Architecture.md`: same.

## Open Questions

- Should `graph.py` be deleted, or kept as a temporary compatibility shim that imports from `pipeline.py` with a deprecation comment?
- Is there any external user or script importing `build_pipeline()` directly? The repo only shows `main.py`, but package consumers may exist.
- Should state default construction live in `main.py` or `orchestration/pipeline.py`? Recommendation: put it in `pipeline.py` so tests and CLI share one default.
